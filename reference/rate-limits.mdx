Every Fade API key is subject to a per-minute request limit that protects service quality for all customers. Understanding these limits — and how to handle them gracefully in your integration — will keep your application running smoothly even during high-frequency polling or batch analysis workflows.

---

## Default Rate Limit

The default rate limit is **120 requests per key per minute**, applied as a rolling window. Every endpoint counts against this limit — including manifest, forecast list, forecast detail, grade, and history endpoints.

<Note>
  If your use case requires a higher rate limit — for example, real-time event monitoring across large numbers of markets — contact Sportshack to discuss a custom limit. Keys can be rate-limited independently, so increased limits for one key do not affect others on your account.
</Note>

---

## HTTP 429 — Rate Limit Exceeded

When your key exceeds 120 requests within a rolling 60-second window, the API returns an **HTTP 429** response. The response body follows the standard error envelope:

```json
{
  "error": {
    "code": "rate_limit_exceeded",
    "message": "You have exceeded the rate limit of 120 requests per minute. Please slow down and retry after a brief pause."
  },
  "api_version": "1"
}
```

Your client should treat a 429 as a recoverable condition. Do not immediately retry — wait before re-sending the failed request.

### Recommended Backoff Strategy

Use **exponential backoff with jitter** to avoid thundering-herd retry storms, especially in multi-threaded or multi-process environments:

1. On the first 429, wait a base delay (e.g., **1 second**).
2. On each successive 429 for the same request, double the wait time: 1s → 2s → 4s → 8s → …
3. Add a random **jitter** of ±20–50 % of the computed delay to spread retries across time.
4. Cap the maximum wait at a sensible ceiling (e.g., **60 seconds**).
5. After a configurable maximum number of attempts (e.g., 5), surface the error to your application layer.

```python
import time
import random
import requests

def fetch_with_backoff(url, headers, max_attempts=5):
    base_delay = 1.0
    for attempt in range(max_attempts):
        response = requests.get(url, headers=headers)
        if response.status_code != 429:
            return response
        delay = base_delay * (2 ** attempt)
        jitter = delay * random.uniform(0.2, 0.5)
        time.sleep(delay + jitter)
    raise RuntimeError("Max retry attempts reached after repeated 429 responses.")
```

<Tip>
  You can verify that your API key is active and healthy at any time by calling the manifest endpoint. A successful `200` response confirms that your key is valid, not revoked, and within its rate limit. Make this check part of your application's startup sequence or health-check routine.
</Tip>

## HTTP 401 — Unauthorized

A **401** response means the API could not authenticate your request. This occurs in three situations:

- **Missing key** — the `Authorization` header was omitted entirely.
- **Invalid key** — the key value does not match any active key in the system.
- **Revoked key** — the key was previously valid but has been deactivated.

```json
{
  "error": {
    "code": "unauthorized",
    "message": "API key is missing, invalid, or has been revoked. Verify your key and try again."
  },
  "api_version": "1"
}
```

Unlike a 429, a 401 is **not recoverable by retrying** — the same request with the same key will always produce the same result. Check your key value and ensure your `Authorization` header is correctly formed before retrying.

<Warning>
  If you receive a 401 and you believe your key should be active, do not attempt to brute-force or guess a valid key. Contact Sportshack to verify your key's status and obtain a replacement if necessary.
</Warning>

## API Key Properties

Fade API keys are designed to give Sportshack fine-grained control over access without affecting your other integrations:

<CardGroup cols={1}>
  <Card title="Customer-Specific" icon="key">
    Each key is issued to a specific customer account. A key cannot be transferred between accounts, and its usage is attributed solely to the account it was issued to.
  </Card>
  <Card title="Independently Rate-Limited" icon="gauge">
    Each key has its own rate limit counter. If you operate multiple keys (e.g., one per application environment), a burst from one key does not consume the quota of another.
  </Card>
  <Card title="Independently Revocable" icon="ban">
    Any individual key can be revoked without affecting other keys on your account. This makes key rotation safe — issue a new key, migrate your application, then revoke the old one.
  </Card>
</CardGroup>

## Quick Reference

| HTTP Status | Meaning | Retry? |
|---|---|---|
| `200` | Success | N/A |
| `401` | Missing, invalid, or revoked key | No — fix the key |
| `422` | Validation error in request parameters | No — fix the request |
| `429` | Rate limit exceeded | Yes — with exponential backoff + jitter |
| `5xx` | Server-side error | Yes — with backoff |
